# Meziverse — how it works

Technical notes for version 2.9.5. Written for whoever picks this up next - including future us.

## The one rule: Ride SillyTavern

Meziverse never reimplements SillyTavern and never touches the chat file behind its back. SillyTavern stays the engine, the UI state and the storage; Meziverse is a scene rendered on top, where **every action is ST's own action, clicked**.

Concretely:

- **Generation, sending, swipes, edits, branches, copy, hide-from-prompt** all click or call ST's own controls and handlers, so every rule ST has (busy gates, empty-input semantics, swipe behaviour, edit autosave) applies unchanged.
- **The chat file is only ever written by ST.** We listen to ST's events; we never write chat data ourselves.
- **Settings** live in ST's `extensionSettings.meziverse`, saved through ST's own `saveSettingsDebounced`. Nothing of ours touches disk.

The single deliberate exception: `body.mz-open .popup` gets a z-lift so ST's own popups (e.g. the new-chat confirm) render above our fullscreen scene. Everything else is scoped to `#mz-root`.

## The scene

- **Mount once, open/close by class.** `#mz-root` is built at boot and hidden; `open()` adds `is-open` (and `body.mz-open`), `close()` removes them. Exit always returns to ST.
- **Two headers.** Meziverse header (34 px): "Meziverse" + the version, the background pill, chat file name, settings + exit. Chat header (48 px): the scene cluster (date, time, place, weather chip) + log button; the cast strip rides just below it, flush on the reading pane (Settings > Images > Avatars switches it off; the pane's height never depends on it).
- **Reading pane** shows the newest message as prose; a drag handle resizes it (persisted in settings). The **log** is a floating, stretchable window listing earlier turns, with per-turn actions and its own remembered size.
- **Message actions** replicate ST's message-header menu as flat icon buttons — no dropdowns — on ALL turns: copy, branch, hide-from-prompt (eye), edit, swipe, download-earlier. Edit opens ST's own `.mes_edit` editor (the pane mirrors `#curEditTextarea` one-way) with an edit bar ✓ / 🗑 / ✕; a 400 ms watch owns edit-state exit, and Esc defers to ST while its editor is open. The **ST-mirror buttons wear ST's own FontAwesome glyph classes**, rendered by `fa()`/`faHtml()` at 11px with the theme's colours through `currentColor` — the eye flips exclude/include (`fa-eye`/`fa-eye-slash`) and send flips to `fa-circle-stop` while generating. The **brush** rides the pane head, right of the card name (ST's `fa-solid fa-paintbrush`), keeping its `bg-generate` action and states unchanged.
- **Reasoning is pane-only.** A head toggle left of the card name (default on, `settings().showReasoning`) reveals the model's thinking as an ST-style expandable above the prose — collapsed on arrival, one open/closed state per pane kept across turn steps and streaming redraws. The read (`prose.js` `reasoningOf`) takes `extra.reasoning_display_text ?? extra.reasoning`, per swipe from `swipe_info[swipe_id].extra`, falling back to an inline `think` body (`tags.js` `readInlineThink`, streaming-safe). The log renders `compact: true` and never draws one.

## Scene info (the first feature family)

The model already emits the state of the story as in-band tags (`scene`, `LEDGER`, the guides — see the plan doc's tag catalogue). Meziverse reads them; it never invents or writes them.

- **Parsing.** `tags.js` tokenizes a copy of `message.mes` with a tolerant grammar: tag names case-insensitive, attribute order free, single or double quotes, optional closing slash, unknown names are not tags (so card-written HTML passes through). `stripTags()` yields clean prose, and `prose.js` hands that to ST's formatter — so regex scripts, Markdown, quotes and every display extension behave exactly as in native ST. Tags are stripped in both modes; only decoration is gated.
- **The last-usable rule.** `scene.js` resolves the governing scene: the last complete `scene` with at least one of date / location / present; a turn without one inherits the latest earlier scene, walking backwards through the chat. Every complete scene still renders as an inline row at its place in the prose — rows live in the pane and the log only, never in ST's native chat (the chat file is never touched).
- **The ribbon has four wardrobes.** One setting (`sceneHeaderStyle`, Settings > General > Scene header) dresses every pane ribbon: **quiet** (the default), **rule** (chapter rule), **date** (date-first) and **simple** (the first band Meziverse ever drew). Same fields, four layouts; the second and later tags look exactly like the first (the divider is structural only). The log drawer keeps its own compact band whatever the setting says. The insets ride `--mz-scene-key/ink/soft/line` per theme with one shared soft dark-grey scrim (`--mz-scene-scrim` — deliberately not black) and a text shadow, so the header holds on any stamped background; the grey-free rule holds — soft is a dimmer white, never grey. Each size is `calc(px * var(--mz-ui-scale))`. Weather follows `weatherTag` alone as a 24×24 stroke glyph (`weatherGlyph` in `prose.js`): unknown or missing draws nothing, and "clear" reads as the sun by day and the crescent at night (hour ≥ 19 or < 6). The free-text weather is never parsed — it prints beside the glyph.
- **The ribbon edits its own place.** The pencil in a ribbon's seat (reading pane only; the compact log band never carries one) turns that ribbon into an editor: the breadcrumb becomes one input per level with add/remove, and the date, time, weather and cast stay read-only. Nothing is written until Save (Esc and Cancel discard; Enter steps through the levels and saves on the last; an all-empty chain disables Save). Saving rewrites **only the `location` attribute of that one scene tag** (`editSceneAttrs` in `tags.js`, entity-safe so quotes round-trip; current swipe only) and the write goes through **ST's own editor** (`editMessage` → textarea → `acceptEdit`), so ST saves, re-renders and fires `MESSAGE_EDITED` — and the map and the background chain re-derive from the corrected location by themselves. Scene edit and message edit are mutually exclusive, and the watch keeps its hands off an ST editor a scene save is driving.
- **Cast.** Names come from `present`, minus the persona, deduped case-insensitively in order. Portraits are per chat — paths in `chatMetadata.meziverse.cast`, keyed by normalised name — uploaded through ST's own `/api/images/upload` as a small WebP. Nothing is auto-deleted. A loaded portrait is clean (no plate, halo or scrim — the name rides a text shadow); those appear only on an empty or broken image.
- **Chat bar and header** read the same scene: date and time (the last time-like piece splits from the date), the whole location string as written, a weather chip when present.

## Meziverse mode

One `mode` flag in `settings.js` (default on) behind a single `modeOn()` accessor — but it is an umbrella for the **extras only**: the ledger rails, the inline cue marks and boxes, the mindscape, the thought bubbles. The base extension never consults it. Off means a non-Meziverse preset is in play: tags are still stripped from the prose and the scene keeps working — cluster, rows, cast and the whole image chain are driven by the `scene` tag contract alone — while the Meziverse.json extras step aside.

The switch is the Settings > Meziverse mode tab's header row, well away from the main UI - it is not meant to be flipped mid-chat; flipping it redraws the turn at once and persists in extension settings. Settings → Meziverse mode carries the **Tracker entries** menu — standing, profiles, shifts, threads, plans, hooks, lore, story so far — each flipping `settings().entries` live (`entryOn(key)`), so mode-on with individual entries off is a first-class state. Phase 5 binds `modeOn()` to the owned preset — only what feeds the accessor changes, never a feature file.

A release build turns the extras off from the source: `DEV_EXTRAS` in `settings.js` is the release switch. True keeps the mode tab and the extras in play; false hides the tab whole (the switch, Tracker entries and Cues) and makes `modeOn()` answer false whatever the stored setting says - the base extension alone ships.

## The ledger rails (the second feature family)

Each reply may close with a `LEDGER` block — the model's full story state as row tags (`recap`, `lore`, `hook`, `thread`, `goals`, `profile`, `shift`, `standing`, `plan`; see the plan doc's tag catalogue). Meziverse only reads it; the model writes it.

- **Parsing is pure and full-state.** `ledger.js` resolves the governing ledger per turn: the last complete `LEDGER` block of the shown message; a turn without one inherits the latest earlier block, labelled "from turn N". A block still streaming is not a block — it falls back rather than showing half its rows. Rows are normalized per catalogue, trimmed and never rewritten, in the tag's own order, and **no row limits are enforced** (display caps are slicing only). `goals` rows are collected and never rendered.
- **Deltas are derived, not remembered.** Standing levels compare against the previous ledger block (`withStandingDeltas`), so each block's signed chips are correct when scrolling back through the chat and nothing accumulates. Shift deltas are different: the tag writes this turn's movement itself (`delta` / `ddelta`), so they are read as written. The shift meters are uncapped (no ceiling, no floor), and each bar's scale is the pair's own recent widest — the total and the one before it — rounded up to the next hundred (`meterMax`), so 101 reads as 101 / 200.
- **The rails** (`dock.js`) are one icon menu per side plus glance columns down the frame: right = threads and a single bordered PLANS card (hooks, lore and story so far are popup-only), left = the chat log first (chrome), then standing, profiles and shifts. An `ENTRIES` registry carries each entry's title, side, box cap and renderers. Nothing draws unless `modeOn() && entryOn(key)` and the entry has rows — no rows, no cards, no placeholder promises. But the **space is always reserved**: at desktop widths the narration pane keeps its width and the columns' icon menus stay on stage whatever the content — only the glance cards are content-driven, so toggling entries or switching chats never shifts the layout. The Tracker entries menu (Settings → Meziverse mode) flips the switches in `settings().entries` live.
- **Popups ride over the narration pane** and open beside their own rail — people left, story right. The fly holds every record of one entry; a profile opens as a full card (the avatar image as head backdrop, every field, the private thought; a reserved foot for relevant shifts later). Esc closes card → popup → log → settings.
- **Text is display text**: `{{user}}` renders as the persona's name; every other value shows exactly as written, with no normalizers on free-text fields. Numbers wear signed tabular numerals; every tone comes from theme tokens.
- **Mobile** (< 760 px): glance columns hide, every glyph rides a slim second chat-bar line under location/date, and popups open as bottom sheets.

Prompt work — pushing this state back at the model — stays out until the preset phase.

## The inline cues (the third feature family)

Four in-band tags decorate the prose itself: `lie`, `filter`, `flashback`, `meanwhile`; `speech` is a fifth voice of its own (the fifth feature family, below). Everything else about tags is unchanged - stripped in every mode, decoration gated on `modeOn()`.

- **Parsing is one scanner** (`tags.js`): `parseTags` finds catalogue tags only (card-written HTML passes through; fenced and inline code is never parsed), `stripTags` gives the plain text, and `splitCues` splits a message into prose runs, scene rows, meanwhile boxes and inline marks — so a swipe, edit or stream frame is correct the moment the text changes.
- **Marks travel as slots.** A mark's private-use placeholder rides through SillyTavern's formatter inside its prose run and is swapped for the markup afterwards, so paragraphs and quotes never break. Placement: the mark sits at the end of the text before its tag; a tag on a line of its own joins the previous paragraph's end; marks stack in reading order. A tag not yet closed draws nothing and hides its tail.
- **One shared popover** (a frame child, fixed-positioned and clamped) serves the lie and blind-spot marks: hover opens on pointer devices after 90 ms, a tap or click pins, focus-visible opens, one at a time. The liar's portrait additionally wears a hairline crack (`renderTells`) that flickers while its popover is open — a bonus echo, never the only carrier.
- **The flashback** leaves a dream pill carrying the body out of the prose and the log; a click opens the mindscape (`cues.js`) — paced fragments on a warmed, blurred stage. The rows come from the mechanical splitter in `memory.js`: sentences split at their own ends, never inside quotation marks, and a sentence that speaks in quotes takes the single one after it. No word lists. Closing the memory fires its cascade on the character's thought overlay until the next turn.
- **The meanwhile box** renders closed and grows in place (`grid-template-rows`), numbered "n / N" when several stack in one reply. Boxes toggle independently and reset closed on every re-render.
- **Floats** (`floats.js`): one `placeFloat` / `closeFloats` registry keeps the popover and the thought overlays to one floating thing at a time. Esc chain: floats → memory → card → dock → log → settings.
- **Settings** (Cues group): Popovers (hover and tap / tap only), Memories (pill / open on arrival), Meanwhile (closed / latest one open). The last two fire once per arrival, on the latest turn, after generation settles.
- **Mobile** (< 760 px): the cue popover stays anchored to its mark — a deliberate deviation from the bottom-sheet rule; the meanwhile box drops its inner indent; the mindscape clamps to the frame.

## The story backgrounds (the fourth feature family)

The chat's background follows the story's place. The decision layer is pure (`backgrounds.js`), the choreography is `bgchain.js`, and every call into SillyTavern stays at the seam (`st.js`).

- **The store** lives in `chatMetadata.meziverse.bg` beside the cast portraits, saved through ST's own `saveChatMetadata()`: one record per drawn place (id, place name, prompt, image path), `currentKey` for the image on screen, ids never recycled. `locationKey` folds case, whitespace and location levels so a place keeps one record whatever the spelling, and a place the watcher calls "same" or "known" has its new spelling aliased onto the image already up - but only after `placeNamesLikelySame` agrees the two names could be one spot (numbers decide: "Corridor C-12" is not "Corridor C-9", "Landing Pad" shares nothing with "Kaffe Station"), because a careless fold would merge two places onto one picture forever. A rejected claim draws fresh instead: the cache grows by meaning, verified - never by trust. A location edit keeps its picture: `reconcileRecordPlace` renames and re-keys the record the edited reply points at (the old name is dropped - the edit says it was never that place's name), so the scene tag and the library never drift apart; an edit naming a genuinely different place falls through to the ordinary re-resolution. **One stamp names one scene.** Each response (each swipe variant) carries at most ONE background pointer, and it belongs to the response's **last** scene tag - where narration stopped, waiting for the user - whatever else that response passed through: a reply moving kitchen → hallway → bedroom draws for the bedroom, and the hallway gets no picture unless some response someday ends there. The map holds itself to the same contract: a response's picture may only attach to the place its narration stopped at; mid-reply scenes are real places (they draw as "passed through" dots and keep their scenes and journeys) but never borrow the response's picture.
- **Every reply remembers its own picture.** The record in effect for a reply is stamped on it — `extra.meziverse.bg`, mirrored into that swipe variant's own `swipe_info[i].extra` slot (ST's per-swipe home) — so it rides the message through swipes, deletions and branches untouched. Resolution at any point in the chat walks: the variant's own stamp, then the nearest stamped variant of the same message (a fresh swipe taken from another variant keeps that variant's picture), then back over earlier messages. User turns are never stamped — a user turn, or a reply that drew nothing, inherits the previous reply's picture exactly that way. Stamps point at records, never image paths: one canonical image per place, and the brush replaces the record **in place** (`storeRecord(overwrite)`), so each manual retry wins over the last everywhere that place recurs - but only when the record IS that place's alone. A record still shared by several keys (a fold from the careless-matching days) is never overwritten in place: the fresh picture takes the brushed key, that place's replies follow it (`retargetStamps`), and the other places keep the record they knew. Folds die one brush at a time.
- **The skip-gate is a string compare, never the change-detector.** `decide()` answers three ways about one reply: it already carries this picture → nothing; the place is known → swap in the cached image; anything else → ask the watcher. The baseline is the picture **the reply carried in** — its own stamp when re-resolving, the story's carried picture otherwise — so a run landing late reasons about its own turn, never the chat's end. Spelling drift ("Pier 9" vs "Pier No9") deliberately falls through, and the watcher verifies sameness **by meaning**.
- **The watcher** is one quiet LLM call through `generateOn` - the Background Agent's own connection on the Connections tab (the current ST API by default) - only what we pass, nothing of ST's prompt plumbing. `buildWatcherRequest` assembles the question: CURRENT BACKGROUND (the place and image description **the reply carried in**), KNOWN BACKGROUNDS (the newest twelve, each description whole - nothing is ever cut), RECENT PLACES, and the LATEST STORY — grouped by scene blocks when the reply carries scene tags (the last block is where the story is; each block's header names the place, time and weather its narration happens in), plain prose when it doesn't: `tagged` picks both the prompt core and the story formatting from **tag presence**, never from the mode switch. The story is stripped to the scene tags and narration (`stripNonSceneTags`) — mood, plot and every other tag are never sent here: this watcher is environment-only, unlike the Music DJ, which reads the story raw on purpose. **The context is the same in every case — do not "improve" this**: whatever the trigger (the brush, or the auto watcher at any pace — 1, 2, N replies between calls), the watcher reads exactly this one question — the last reply plus the current background, the library and the places timeline. The pace throttles **how often** the call happens, never **how much** the watcher reads — and the skip-gate means an unchanged location never reaches the watcher at all. The question is "does the picture still fit this reply?", not "what happened recently?": never widen this window, couple it to the pace, or send raw chat turns here (raw story is the DJ's logic, for mood and plot; this watcher is environment-only). Every place is labeled `short name [World location: ...]` - the short name (the chain's last segment, "Unit 4B - Bedroom") names the picture, the chain is the world it lives in, and the leaf rides first so it is always the first thing read - and every image description sits behind an explicit `Description:` marker, so the description never reads as part of the name. The four blocks wear their own tags (`<currentBackground>`, `<knownBackgrounds>`, `<recentPlaces>`, `<latestStory>`) with the library's title reading KNOWN BACKGROUNDS (IMAGE LIBRARY); the request's block-tag names are scrubbed from place and story text (story is untrusted and may carry look-alikes), so the layout can never be spoofed. The style suffix is appended at draw time and the record keeps the description raw; the fallback template (watcher failure, or a forced draw whose answer carried no description) speaks image-model: the spot first, its world as plain words after it (never a "|" chain), the weather and a day-part for the light (never a calendar stamp), then the shot tags. The question is scoped to the reply being resolved (`at`): its story is the story **up to that reply**, never the chat's end, and only the reply's final location counts — mid-reply hops are ignored. Answers parse as one JSON object (`same` / `known` + id / `new` + place + image prompt) with a plain-text fallback (`SAME`, `KNOWN <id>`, `NEW`…); the JSON format is appended to the system prompt **by code**, so user edits to the prompt cores cannot break parsing. Structured output is deliberately **not** requested: some connections reject `response_format` outright (422), and the answer is read from the text anyway - the same way the music DJ reads its intent. `getLastWatcherRequest()` keeps the last question verbatim for the settings panel. The call passes no `responseLength`: on providers that count the prompt against the budget, any cap starves the answer to nothing - the global response length stands instead.
- **The prompt cores are editable** (`bgPromptOn` / `bgPromptOff`, defaults `DEFAULT_BG_PROMPT_ON/OFF`): 40–90 words of comma-separated visual phrases, the place as the subject — no characters, no names, no actions, no quality tags; lighting and sky anchored on the story's time of day and weather.
- **Drawing rides ST's Image Generation** (`sd`, declared `optional` in `manifest.json`): the `/imagine` callback invoked with `quiet:'true', gallery:'false', extend:'false'` — no chat message, no sd rewrite or review window. Quiet discards the prompt, so we keep our own record. The image comes back as a path and becomes the background by emitting `FORCE_SET_BACKGROUND {url, path}` — ST then locks, registers and persists it (Backgrounds → Chat). `imageGenerationStatus()` turns the missing/unconfigured case into words, not a stack trace.
- **The scene mirror speaks only in authored urls.** Our `FORCE_SET_BACKGROUND` listener may run before ST's own handler repaints `#bg1` (registration order), so the payload's `url()` is applied directly, with one deferred re-read as insurance. Every probe reads the INLINE value only: `getComputedStyle` reports a running `background-image` transition as `cross-fade(...)` machine syntax (Chrome interpolates that transition, Firefox flips it discretely - which is why the same code behaved so differently across browsers), and that syntax is poison in a custom property: one substitution kills the declaration and blanks the scene. `sceneUrl()` vets every candidate; an unusable stranger is dropped and the last good picture stays.
- **Weather lives on the background stage.** One `.mz-weather` layer at the tint's old slot: over the background and its soft twin, behind the cast, rails and narration pane. The scene tag's `weatherTag` names the state (aliases fold, unknown shows nothing) and `locationTag` gates it strictly to outdoor; the free-text weather's tone words tune its strength in three tiers. Particles are spawned once with desynced clocks and only cross-fade between states (`data-mz-wx` / `data-mz-wx-int` on the frame) - no DOM churn, no per-frame JS, transform and opacity only. The sun's place comes from `scene.time`'s hour on a 6h-20h arc - the same clock that lit the painted backdrop - and night hours dim the set to a cool whisper. Reduced motion freezes every particle mid-fall (a still photograph) and lightning never fires. The dark wash over images is commented out in `20-shell.css` - it may return as the daycycle (day/night) layer. Indoors the layer plays the quiet twin: effects seeded per place (candlelight, hearth, window light, dust, lamp), the window's light colored by the clock.
- **The glass reads our own scene, never the page behind.** One scene in two layers: the base reads sharp across the frame, and the soft twin (the pane blur slider's var, `saturate(140%) blur(...)`) lives in the narration pane's box alone - clipped to the pane's own geometry (`clip-path: inset(... )` built from the pane's height, gutters and radius), so the blur edge IS the pane's border line, corners included, and nothing bleeds beside it. The blur is the pane's read and nowhere else: the chrome, the rails and the stage read sharp through their tints. No `backdrop-filter` anywhere in the extension: Firefox's compositor samples those wrong when filtered pages sit behind the glass, washing the grey of ST's theme over the whole UI on screen while screenshots stay correct (ST's own `no-blur` toggle, which kills every backdrop filter, confirms the cause). The mirror feeds both layers through `--mz-st-bg`.
- **One job per reply, one at a time.** Work is target-scoped — one reply, one swipe variant — and queued: an image in flight is never doubled, a newer job for the same reply replaces the older (force beats re-resolving beats arriving), and a chat change cancels everything. Every run reports a status: `off | unchanged | cached | generated | superseded | cancelled | unavailable | error`. Every landing stamps the reply, saves the chat, and re-asserts the **shown turn** — so a result landing late updates its own reply's history and never yanks the picture out from under whatever turn is being read. Triggers: `GENERATION_ENDED/STOPPED`, `GROUP_WRAPPER_FINISHED` re-resolve the chat's end; `MESSAGE_EDITED` re-resolves the edited reply; `MESSAGE_SWIPED` draws nothing - a stamped variant's picture comes back by swap, an unseen one keeps the picture it swiped from, and a genuinely new place wants the brush; `CHAT_CHANGED` cancels, resets the generation pace, and re-derives the current key from the background ST itself restored. The watcher is for new turns only. One plan table (`planResolution`, pure and tested) branches every run on tag presence: `scene` present runs the decide chain (free outcomes — a skip's "none", a cached swap — always run at any pace, so stamps stay truthful); no tag falls to the plain-prose watcher at pace, keeping the last picture between fires and flagging the miss with one notice per chat. **The chain follows the chat only while the scene is open — the master switch.** Closed or never opened, every handler above and `requestBackground` itself return without a call, a write or a fetch (the injection to come rides the same gate). Opening catches the chat up - metadata re-derived, the shown turn's recorded picture re-asserted (swap-only) - and draws nothing: the watcher is for new turns, and a chat whose opening wants a picture presses the brush. Closing kills work in flight, resets the pace, and hands the chat's background back to what the chain found before it took over — the **takeover baseline** recorded once per chat (`store.baseline`: the lock and the shown image at the chain's first write), or SillyTavern's own `/unlockbg` for a chat drawn before the baseline existed - a baseline of nothing to hand back takes the unlock too, so the screen gets a picture back, never a hole. A background the user took back while we ran (unlocked, or locked their own) is theirs: exiting stands down. A chat change while the scene is closed hands that chat back the same way, so no chat ever shows a Meziverse picture with the extension off.
- **The shown turn owns the screen.** Scrolling the transcript hands the chain the shown turn (`setShownTurn`), and the swap (`syncShownBackground`) is read-only: the stamped picture comes back — shuffle back through the turns and the pictures shuffle with them — never asking, never drawing. Chats without history fall back to the cached picture of the shown place; a user turn inherits the nearest reply's picture before it. Closing the scene hands the chain the chat's end again.
- **Stage notices** ride the toastr interception as sticky notices (`timeOut: 0`): "Envisioning the location…" while the watcher answers, "Painting {short name}…" while the image draws — dropped when their stage ends — then a brief "Background set: {short name}". Every notice names the leaf, never the whole chain. Every error seam goes through `errorText()` (`st.js`), which unwraps throwables: never "[object Object]".
- **Settings** (Images tab, Backgrounds section): auto follow, the **Background generation pace** (shared by both modes, default 1 = every AI response; only AI turns count — user turns never — and swipes and edits do; the brush never waits or counts), size (landscape / square), style, negative, the two prompts — "Watcher prompt · Scene tags" and "· Plain prose", each picked by the reply's tag presence — with "Restore default" and "Show last request", and "Draw one now" - the brush, which runs the chain with `force` on the response it was clicked on (the shown reply, read from the pane at click time - never a stale reading, never the chat's end behind the reader's back; a user turn takes the nearest reply before it, since user turns own no picture): a fresh image whatever the watcher answers, the place's record replaced in place - each retry wins - no review window.

Known limits, by design for now: the tagged skip-gate never consults the watcher when the location string is unchanged (a radically reimagined same-name place needs the brush); the no-tag path is deliberately basic — a fixed pace, keeping the last picture between fires.

## The speech bubbles (the fifth feature family)

Spoken lines wear a bubble in the reading pane. One complete `<speech character tone>` tag becomes one inline cue (`splitCues`), its slot riding through SillyTavern's formatter exactly like a mark's - so the narration runs around it and paragraphs never break. The pure read lives in `scene.js` (`describeSpeech`: character, tone with `mood` accepted beside it, `body` as authored, `words` with one matched outer quote pair lifted - the bubble is the quoting). The label carries the cast's thumbnail when avatars hold a picture for the `castKey` of the name - the one-word-name contract shared with `present` is what maps speakers to portraits - and falls back to the name alone; the tone is a tiny italic after the bubble. Bubbles are the pane's own (`compact` is the log) and ride their own `speechFx` switch; wherever they do not render, the words fall to plain prose with their quote marks, exactly as the format writes them. The display form is deliberately the quick placeholder - the presentation modes (avatar-forward forms) are designed later.

## The music player (the sixth feature family)

The scene's soundtrack, played from YouTube: a compact player in the header that undocks into a draggable card on wide screens. `music.js` owns the widget, the embed and the request read; the pure half (`parseVideoRef`, `readMusicTag`, `thumbnailUrl`, `clampVolume`) is tested.

- **Two ways to start it, both by hand in this phase.** Paste a YouTube link, a video ID, or a song name into the player's own input, or let the story ask: a reply may carry one `<music>` tag (body or `query` attribute, optional `mood` for display) and the reply landing plays it. A request that is a **link or id plays at once**; a named song is **searched** with the user's own YouTube Data API key and the best candidate plays - without a key it is remembered and shown ("add an API key to play named songs"), never played blind. The tag is a hidden tag in the catalogue: the request is metadata, never prose. One reply cues once - a re-run of the same turn never restarts the track.
- **Song search is the user's own free key, in the browser** (`musicsearch.js` is the pure half: query building, result filtering, error wording). The API's `videoEmbeddable` filter is the floor - a video that cannot embed cannot play here - and our own filter drops Shorts, memes and reactions by title, over-fetching so the survivors fill the list. A query asking for long form ("one hour", "mix", "OST") gets `videoDuration: long`, with a plain fallback pass when that comes back empty. Results are cached for the session (repeated requests cost no quota), the candidates are **verified against `videos.list` before any frame loads** (1 quota unit against the search's 100 - the embeddable flag can go stale), and the **top candidate plays, with a blocked or gone one falling through to the next** before any error shows. The key restriction guidance is the mirror image of a server proxy's: searches run in the user's own browser, so a key restricted by HTTP referrer is the right lock here - and the search fetch pins its referrer for the same reason the embed does (below).
- **The Music DJ is its own watcher** (`musicdj.js`): after each new reply - at a set pace, at most one call every N AI replies - one quiet watcher call (riding the Music Agent's own connection - see The Connections tab) reads the story and answers one JSON intent (`play` / `volume` / `none` with a mood and a search query; Marinara's YouTube DJ contract, paraphrased). The story rides as **the chat's own recent turns** - raw, tags and all, user turns included, with the latest story turn kept apart as the turn to judge (`history.js`, the DJ's own story reader — the background watcher deliberately differs: scene-grouped, environment-only, one reply): the only cleaning a turn gets is the user's own SillyTavern prompt regexes, applied per turn at its depth exactly as the main chat does - never anything of ours, because presets hide story cues in tags and with mode off any preset is served. Deliberately **independent from the background watcher**: its own switch (opt-in, like `bgAuto`), pace, editable prompt core and call, reaching the player only through a controller - so backgrounds and music combine in any on/off pairing, and each watcher can ride its own model (the Connections tab). **Pick style** chooses what the DJ reaches for - **Orchestra** (an instrumental score, never vocal songs) or **Songs** (one specific real song as "Artist - Title", the official or artist upload preferred) - and both take the genre from the story itself, so a Wild West tale, a sci-fi tale and a medieval tale never pick alike; both fall back to a precise vibe query rather than invent anything. The pick style and the answer format are appended to the system prompt **by code**, so prompt edits cannot break parsing, and an unreadable answer is `none` - the DJ failing never stops what plays. A reply whose `<music>` tag already cued a track is the story's own and the DJ never overrules it; a repeated pick rotates past the track already playing; **Fresh pick** on the player is the manual trigger - it lives whenever a search can run, the Music DJ switch (the auto watcher) notwithstanding - and asks again with the order to choose differently. The call passes no `responseLength` (a cap starves the answer on providers that count the prompt against the budget). The prompt's rules cover what the search must never receive (Shorts, memes, reactions) and the volume bands (20-40 quiet, 60-85 action).
- **The embed inherits SillyTavern's `Referrer-Policy: no-referrer`** - and YouTube rejects embeds that arrive without a referrer: every video dies with error 150 while the thumbnail and metadata still load fine (the "cannot be embedded" trap). The official embed snippet's `referrerpolicy="strict-origin-when-cross-origin"` is the cure, so that policy - with YouTube's official `allow` list - is pinned on `player.getIframe()` right after construction, before its navigation task runs. The same trap catches a typed `/embed/` URL (typed navigation has no referrer either) and every `fetch` from the page (which is why the search fetch pins its own referrer). YouTube's own controls are off (`controls: 0`) - the widget is the control surface - and an embed born inside a `display:none` box fails identically, so the stage always renders (clipped, never `hidden`) while a track exists. Failures sort by class (`errorClass`): a transient one - a stream that would not load - buys one rebuild-and-retry, while a blocked or gone video (100/101/150/153, and any unknown code) goes **straight to the next candidate**, its own title and channel carried along, and only an exhausted list speaks - with a "Watch on YouTube" link in the panel. The player runs YouTube's privacy-enhanced `youtube-nocookie.com` host: no cookies until the listener interacts, which also quiets the cross-site cookie noise Firefox logs for youtube.com frames on every load. A rotating pick also skips the tracks just heard (a session list of five), so a fresh pick is never a repeat.
- **The widget** is one root with two faces: a **pill** in the header (art, a ticker that glides when the title overflows, play, more, undock) and a **card** - the same element, dropping under the pill when opened docked, or standing alone as the floating player when undocked (wide screens only - a narrow one re-docks it at once rather than let the card cover the story). The card carries the track's own cover blurred behind its top, the grip (status line + window tools), a two-line clamped title with the channel and the mood chip, a seek row with times (a 500ms clock read while the embed plays; a live stream hides it), and the transport - volume left, stop/play/fresh-pick centre, video right - above one search field. **The whole card is the drag handle** (controls exempt): a 4px threshold keeps clicks clean, a release near an edge snaps softly to the 12px gutter, arrow keys nudge the grip, a double-click shrinks it to a one-row mini (`musicMini`). Errors live in the note with the "Watch on YouTube" link, never in the title; while any DJ call is in flight the player itself reads "Selecting track..." - a loader in the widget, never a toast.
- **The stage is never `display:none` while audio plays.** The embed lives in one fixed frame-level stage (the cue-popover idiom); with the video panel closed it is clipped to nothing (`clip-path: inset(50%)`, opacity 0) instead of hidden - an embed that goes display:none takes its sound with it in some browsers. The stage sits under the widget, clamped, flipping above at the bottom edge.
- **The master switch governs sound too.** With the scene closed, requests are ignored and whatever is playing pauses; the widget rides `musicOn()` (Settings > Features > Music), and **Story requests** gates the `<music>` tag separately so hand-played music can live without story cues. The Music group also carries the API key row (save/remove, "Key configured"), the **Music DJ** switch and its **pace**, the **Pick style** segment (Orchestra / Songs), **DJ prompt** (with Restore default) and **Show last request** - the same verbatim-question panel the background watcher keeps. A saved prompt core that still holds an older default follows the default forward (settings.js refreshes it); an edited core is never touched. Volume, mute, dock state and the card's spot live in `extensionSettings`; the track itself is session state - per-chat history is future work.

## The map (the seventh feature family)

The story's places as a live atlas: a minimap window in the corner and a full map window, both drawing the same contour chart - territories as soft land, places as picture pins, journeys as dotted legs with a mode glyph. `mapdata.js` is the pure core (scene tags → places, journeys, layout) and `map.js` is its stage; the atlas is **derived on demand and thrown away** - nothing about places is stored. Node identity lives in `node.key`, the folded path ("usa/new york city/choi house/kitchen"; mobiles "~jins lotus emira"), so selection, the saved view and the curator verdicts to come survive every rebuild. Master-switch gated like everything: with the scene closed nothing is derived or drawn.

- **Only the selected swipe variant maps.** An unselected swipe is branch material the story did not take: the map reads `swipes[swipe_id]`'s text and that variant's own stamp (`activeStamp`), never a sibling's - flipping the selection flips the map, automatically, because the atlas is derived. An unstamped selected variant contributes no place at all (unlike the stage, a discarded branch never lends its picture).
- **The En Route rule: route context is not a place.** A chain carrying `en route` (or a legacy transient spot above a known vehicle) places nothing at or above the keyword - the prefix of a leg cannot be trusted - and the level after it is THE vehicle: one mobile node per folded name ("~jins lotus emira"), shared by every trip and every parked stop. Trips become journey legs (`deriveLegs`), parked stops anchor as spots of their place ("Local Cafe Parking Lot | Jin's Lotus Emira" is a spot of the lot), and a chain of pure route context is a transit observation - remembered, but placing nothing. The churn analysis remains the evidence for old chats without the keyword.
- **Journeys are legs, not containment.** Each observation's location is its node (or the place a parked vehicle sits at); a located scene somewhere new closes a leg carrying the mode read off the vehicle's name (`travelMode`, generic route glyph for a walk or an unknown name). Trips between the same two places pile onto one leg with a count, a move between two spots of one place is not a journey, and a story ending in transit draws an open stub. Leg endpoints draw to `anchor(id)` - the nearest pin at or above a node - so depth collapsing never loses a journey.
- **The layout never moves a place.** No coordinates live in the data; `layoutAtlas` generates them deterministically, seeded by the folded name. Placement is first-appearance order, append-only, with a search radius independent of the item's own size - the three ways a newcomer could jump an existing place are all closed. Documented limits: a territory whose subtree grows may still nudge its slot, and a transient-looking name WITH children ("Main Street | Building 5") stays a real place - both deliberate departures from the design reference's draft.
- **Stops and passed-through - pictures follow the bg watcher's contract.** A response carries ONE picture pointer and it names the response's LAST scene tag (see the backgrounds family above); so a scene may claim a picture only when its response stopped there, and the kitchen a response walked through never shows the bedroom that ended it. Places a response ever stopped at draw as **picture pins** (latest drawn background, map glyph when none); places only ever passed through draw as **smaller flat dots** and promote by themselves the moment a response stops there. The details card follows the same rule: image space only where a scene ended, never on a region or territory.
- **Two windows, one chart.** The minimap is a crop of the same SVG around the story's place (recent leg kept in frame where it fits), with its own zoom and size; the full window pans and zooms the same world and pairs it with a text index, a place card (Seen timeline with the visits and their Turn buttons, Who, Journeys), a cartouche, layer toggles (journeys / flags) and Fit/Now. Both windows drag by anything that is not a control (the 4px threshold separates drag from click; pointer capture engages only once a drag IS one - capturing on pointerdown retargets the click and kills buttons), both resize and remember their box, and the index is a tree folded to the story's own branch.
- **Flags are display only.** Possible duplicates, ambiguous names and mobile-suspects render as badges and ties and never merge anything: the map curator is the map's Part B - keyed verdicts in `chatMetadata.meziverse.mapCuration`, auto-applied only in Auto mode with Undo, user clicks always winning. Until it lands, `buildAtlas` answers everything itself and the flags merely point.

## The Connections tab (where watcher calls ride)

Each watcher agent rides its own LLM, chosen on Settings > Connections. One engine, many doors (`connections.js`): `generateOn(agentId, request)` takes the watcher's usual `{prompt, systemPrompt}` and answers the usual `{ok, text, error}` whatever the door - the **current ST API** (today's `generateRaw` path, untouched), a **Connection Manager profile** (ST's own `ConnectionManagerRequestService`, its presets and instruct template applied, Chat and Text Completion alike), or a **custom OpenAI-compatible endpoint** (`{model, messages}` on `/chat/completions`, Bearer key). Two rules ride every route: no response length cap (providers that count the prompt against the budget starve the answer to nothing) and never structured output on the wire (some connections reject it outright; answers are read from the text).

The **Background Agent** and the **Music Agent** are the same section component - one line each in `CONNECTION_AGENTS` (the section factory renders them in order) plus one `generateOn` call at their watcher, never a second copy of the logic; the map agent joins the same way in its own batch. The Music DJ reaches the ride through its controller (`ask`), the same door it reads its settings from; the background watcher calls `generateOn` directly. A **Test** button sends one tiny call through the chosen door and answers inline. The custom API key is saved in `extensionSettings` like every other setting and used only from the user's own browser.

## The composer

Our textarea and ST's `#send_textarea` stay **mirrored both ways** while the scene is open:

- Our input events write into ST's box (dispatching a real `input` event, so ST's auto-fit, draft save/restore and slash-command processing all run).
- ST's box's input events mirror into ours — which is how an **impersonate draft** (ST writes the result into its own box) lands in our composer and stretches it.

Buttons, all clicking ST's own elements:

- **☰ menu** → `#option_start_new_chat` / `#option_back_to_main` (handlers are bound cold; the hidden ST menu never needs to open). Back-to-parent visibility reads `chatMetadata.main_chat` — the same field ST's own `showBookmarksButtons` uses. ST's OK/Cancel confirm renders above the scene via the z-lift.
- **Impersonate / continue** → `#mes_impersonate` / `#mes_continue`, disabled while generating.
- **Send** → non-empty: fills ST's box and sends through it; empty: clears ST's box and clicks `#send_but`, so **ST's own empty-send semantics decide** (plain AI response, or continue when "Continue on send" is on).
- While generating, send becomes the red **stop** (`stopGeneration()`).

Enter sends, Shift+Enter is a newline. The box grows with content via `field-sizing: content` (same CSS as ST's own box, capped at 50 dvh) and is drag-resizable (`resize: vertical`).

## Theming

Three layers of variables: primitives (raw hex, font names, px, ms) → semantics (`--mz-bg`, `--mz-text`, `--mz-accent`, …) → one block per theme on `#mz-root` (`data-theme="ink-jade|ink-amber|ink-rose"`). Components only ever use semantic tokens; translucent chrome is built with `color-mix()` over those tokens, never hardcoded rgba — that was a bug class we fixed once and never want again.

The settings sheet is four tabs: **General** - Appearance (theme, background: none = navy-teal gradient or ST's current, interface scale, pane transparency and blur), Type (narration size and font, prose colour mode: theme / ST / custom with four colour pickers), Motion (reduced motion); **Features** - the Avatars, Backgrounds, Weather, Speech, Music and Map sections; **Connections** - one section per watcher agent (Background Agent, Music Agent): current ST API / ST profile / custom endpoint; **Meziverse mode** - Mode, Tracker entries and Cues. The open tab sticks for the session; every section header is a fold, closed by default, and opening one closes the rest.

## Notices

While the scene is open, ST's `toastr` is intercepted — but its contract survives. The wrapper calls the **real** toastr and returns its real toast element (ST's own consumers keep that element and hand it back to `toastr.clear`, so it must stay intact), while each toast is mirrored as a Meziverse notice dropping from under the header, tinted by kind (success = accent, info = neutral, warning/error = warn/bad tokens). `clear` / `clearAll` dismiss the mirrors too, and `timeOut: 0` means sticky — the background chain's stage notices ride that convention. Message text follows one rule at every seam: never "[object Object]". On close, ST's toastr is restored untouched.

## Events we listen to

`CHAT_CHANGED/LOADED/CREATED/DELETED/RENAMED`, `MESSAGE_SENT/RECEIVED/SWIPED/SWIPE_DELETED/EDITED/DELETED/UPDATED`, `MORE_MESSAGES_LOADED`, `GENERATION_ENDED/STOPPED` → full refresh; `STREAM_TOKEN_RECEIVED` → queued refresh. `GENERATION_STARTED/ENDED/STOPPED` and `GROUP_WRAPPER_FINISHED` → `is-generating` on the frame (send → stop, inputs readonly). `FORCE_SET_BACKGROUND` → the scene's background mirror. The background chain listens to `CHAT_CHANGED` (cancel + re-derive) and `GENERATION_ENDED/STOPPED`, `GROUP_WRAPPER_FINISHED`, `MESSAGE_EDITED` (run once); `MESSAGE_SWIPED` only re-asserts the shown picture. The music player listens to `GENERATION_ENDED/STOPPED` and `GROUP_WRAPPER_FINISHED` (the new reply is scanned for a `<music>` request) and `CHAT_CHANGED` (forget what was handled). Every listener is master-switch gated: with the scene closed, the extension sits idle — nothing runs, nothing is fetched, nothing is written.

## Conventions worth keeping

- **The two watchers are two agents.** The background watcher (`backgrounds.js` / `bgchain.js`) and the Music DJ (`musicdj.js`) are different modules with different logic and are to be treated as such: each its own story format, prompt, pace, switch and call. Never unify their story reads or share their protocols — the background watcher is environment-only (the last reply, scene-grouped and tag-stripped, one fixed context whatever the pace), the DJ is mood-and-plot (raw chat turns). A fix for one must never reach into the other.
- No bundler; plain ES modules at repo root. `manifest.json`: `js: index.js`, `css: style.css`.
- All selectors/ids/classes prefixed `mz-` / `--mz-*` / `#mz-root`.
- Tests: `npm test` (plain `node --test`) over `test/*.test.js`. Synthetic strings only — never a line of real story text from a live chat.
- Before shipping: `node --check` every `src/*.js` (copy to temp, rename `.mjs`), brace-balance the CSS, then push → `git pull` in the deployment clone → reload the tab and confirm the served file actually changed (a reload can silently fail in an embedded browser).
- ST formatter output to expect: `<p>` wrapper, `<br>` newlines, `<q>`, `<em>`, `<strong>`.

## What comes next (not built yet)

The **speech presentation** is the near work: v2.7.0 landed the bubbles as the quick functional form (name label, thumbnail when the cast has one, tiny tone) and the user's designer is suggesting the display modes for when the speaker wears an avatar. Then the preset phase: mode ownership, trim, Features/Style, and the prompt work (`ctx().setExtensionPrompt('meziverse_state', …)`) where the state Meziverse already parses gets pushed back at the model — with the automatic prompt injection riding the same gate as everything else (the scene open, or nothing). The two injections - the narration-start rules and the dialogue format - ride last, as fixed hidden constants, once testing and tuning are done; until then the author's note simulates them and no prompt is pushed. The log drawer keeps plain speech prose for now - it is headed for changes of its own. Richer no-tag detection and general polish/bugs follow (the kept background candidates — the prompt-review popup on the brush among them; the same-name deep check and the per-place regenerate UI were dropped deliberately, the per-response stamps covering regenerate at the data level — the plan doc remembers them). Milestone firing (`shift` totals crossing ±100) is deliberately unimplemented: the idea is to detect the crossing in the extension and fire it from there rather than trust prompt memory. The map's near work is its Part B, the **curator**: the display-only flags (possible duplicates, ambiguous names, mobile-suspects) get judged by low-token `generateRaw` verdicts, keyed overrides in `chatMetadata.meziverse.mapCuration`, applied automatically only in Auto mode with Undo - user clicks always win - and default Off until real chats have been reviewed. The phone is the intended UI, and its buttons are placeholders for now. The background module keeps its own `Background_Module` branch - the watcher's connection choice landed as v2.9.2 and more background work follows there.
